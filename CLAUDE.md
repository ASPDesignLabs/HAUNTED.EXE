# HAUNTED.EXE: notes for whoever works on this next

A Halloween screensaver for Windows that runs in real VGA modes, written in C with no dependencies
beyond the standard Windows DLLs. Two scenes take turns: **HAUNT.EXE**, a possessed 486 PC in 80x25
text mode (720x400), and **CATACOMB**, a Catacomb 3-D / Wolfenstein-style crypt crawl in mode 13h
(320x200, 256 colours) that plays itself and that a person can take over by holding H for three
seconds. Everything is generated by the code: art, textures, music and effects (the caster's hand and
face and the cat merchant were traced from the owner's photographs).

Current release: **1.0.0b21.5**, "First Steps" (pre-release, November 2026; the first two levels drawn, and the lessons on them). Project page:
https://aspdesignlabs.github.io/HAUNTED.EXE/ · repo: `ASPDesignLabs/HAUNTED.EXE`.

## How to use these notes

This file is short on purpose. Every session reads all of it before it does anything, and so does every helper a
session starts, so it holds only what all of them need: the rules, where things are, and where to read. Until the
tidy-up (docs/PLAN-tidy.md, step 6) it was 250 KB; what it held is in `docs/` now, word for word, to be read when it is
wanted:

| Read | For |
|---|---|
| A plan's hand-off log (`docs/PLAN-*.md`; the table under *Where the work stands*) | Any work a plan covers. **Read its log first:** it says where the last session stopped. |
| `docs/catacomb/<subject>.md` (the table under *Where to read about CATACOMB*) | How a system works, and what its functions, state and switches are called. |
| `docs/HARNESS.md` | The harness's commands and environment, every debug switch, the events it logs, how the long runs are made and read, the sanitizers, Windows under Wine. |
| `docs/SAVES.md` | The save's format, version by version. Read it before touching anything that is saved. |
| `docs/KNOWN-ISSUES.md` | What is known to be wrong or untried, and the numbers from every round of balance runs. |
| `docs/HISTORY.md` | What each release and plan was, who settled what, how it was tested and on which branch. |

Don't read them all. Read the one the work needs, and the part of the code it points at.

## Working with the owner

- They play it by hand on their own Windows PC and report back. Mouse feel, sound and input capture
  have been confirmed by hand on real Windows. Anything new is untested by hand until they say so;
  say which parts were only tested in the harness or under Wine.
- For big features they want options and questions first ("bounce a few things off of me before we get
  started"), then they pick. Smaller decisions: pick a sensible default, say so, carry on.
- Honest status matters: the README's "What has been verified" and the page's "Beta status" table say
  exactly what was tested and how. Keep them true, including bad news (e.g. the wider crypt made the
  autopilot die more often; the numbers are in the README).
- British spelling in user-facing text (colour, armour). The README, page and in-game text have a
  plain, slightly dry, literary voice; match it. Code comments are short and in the same voice.
- No model identifiers in commits, code, comments or docs. Commit and PR attribution: follow whatever
  your environment specifies.
- PLAN-combat is built by two agents on one branch (`claude/inspiring-archimedes-dbj5n6`), a track each. Pull with
  rebase and build before every push, never force-push, change only what your track owns, and add to the marked lists only
  above your own track's end mark: docs/PLAN-combat.md section 17 has it all.

## Standing rules

Gathered from where they were first written. Each still holds.

- **Work reaches main at the owner's word, as one squashed commit.** A work branch's own commits never go to main.
  1.0.0b5 was squashed so that an early commit listing the console's codes never reached main; keep it that way.
- **The console's codes are secret.** They are in the source only as hashes (`CON_CODES`) and a scrambled list
  (`CON_HELP`). Never write them in the repo, the README, the page, a commit message or a comment; the owner keeps the
  list.
- **Say how a thing was tested.** "Harness only" until the owner has played it; say so when nothing ran under Wine, and
  when CI alone compiled the Windows and browser builds.
- **The page and the README's "What has been verified" describe the released build only**, with real numbers and the
  bad news. Change the page in the release commit, not before.
- **Release notes say what a player needs to know**: no background work, technicals or debug switches. A full record,
  when one is wanted, goes in `docs/` as `docs/CHANGES-1.0.0b14.md` did.
- **The sanitizers stay clean.** `make asan`, then long runs of the dream and of a scripted player with
  `ASAN_OPTIONS=detect_leaks=0`. Every round so far has been clean.
- **A change to the balance is weighed on many seeds against the build before it** (a `git worktree`, the same seeds):
  eight at the least, sixteen when it matters, since eight carry noise of about a quarter either way. Put the numbers,
  good or bad, in `docs/KNOWN-ISSUES.md` and the README.
- **A change meant to move nothing must be proved to.** For code moved, cut or commented: `sh tools/tidy_check.sh`. For
  work that is visual only: nothing in the simulation, the saves or the dream's numbers may move, and the dream's log
  must match the build before, line for line.
- **Saves outlive releases.** What is added to a save needs a new version or a new section of the ledger, and every
  older save must still load. New kinds of creature go at the end of the list (`MOB_*`): the record is packed for 24
  (`REC_KINDS`), and 23 are taken.
- **Eyes.** Every creature that has eyes shows them bright from anywhere, in any light and fog; the Shade alone is
  excepted (docs/InitialArtPass.md).
- **New art goes to the owner as a sheet before it goes in the game** (`make sheets`, or a mock-up's tool), unless they
  have left it to your judgement. Sheets that were approved are kept in `media/sheets/<pass>/`.

## Building and testing

```sh
make host                 # build/host: the harness (needs gcc, zlib)
make build/host_debug     # with -DHAUNT_DEBUG -DCRAWL_DEBUG: debug switches and event logging
make asan                 # build/host_asan: the debug harness under AddressSanitizer and UBSan
make smoke                # both scenes, a scripted player, a 60 s benchmark (CI runs this)
make scr                  # dist/HAUNTED.scr (needs x86_64-w64-mingw32-gcc); make zip for the package
make cards                # title cards (needs Pillow)
make web                  # the browser's build in build/web (needs emcc: Emscripten 6.0.13, as CI pins)
sh tools/build_site.sh /tmp/site   # the page, as Pages will publish it
sh tools/tidy_check.sh    # proves a change that should move nothing moved nothing: every object against 1.0.0b21.5's
```

On Linux the Makefile keeps each file's object in `build/obj/<rel|debug|asan>/` and compiles as many at once as there are
cores (docs/PLAN-tidy.md, step 3), so a change compiles only what it touched: `scene_crawl.c` 35 s, `crawl_art.c` 18 s, most
others under 5 s, and nothing else with them (before, any change compiled everything: 71 s for the harness, 226 s for all seven
binaries; now 43 s from nothing). The compiler records what each file `#include`d, so a header compiles again exactly what
reads it. `make -j1` for one at a time; `make clean` after changing `CFLAGS`. The Windows and browser builds are still single
commands.

The harness's own commands, its environment (`HOST_INPUT`, `HOST_LOAD`, `HOST_SLOTS`), the debug build's switches
(`CRAWL_SEED`, `CRAWL_LEVEL`, the `CRAWL_TP*` that stand you before a thing: about 160 in all), its `EVENT` lines and the
way the long runs are made are in `docs/HARNESS.md`. Three things to know before opening it:

```sh
build/host shot crawl 5,20,40 /tmp/f                               # frames of the dream at those times
CRAWL_SEED=3 CRAWL_RUNID=7 build/host_debug apl crawl 3000 > log   # the dream for 3,000 s of its time: its state and EVENT lines
HOST_INPUT="1:+H;4.3:-H;5:+W;7:-W" CRAWL_TITLE=0 build/host_debug shot crawl 6,8 /tmp/p   # a scripted person, past the title
```

A fixed `CRAWL_SEED` and `CRAWL_RUNID` give the same log every time, but for lines that print a time taken. Holding H in
the harness meets the title screen unless `CRAWL_TITLE=0`.

## Releasing

1. Update `README.md` (features, "What has been verified" with real numbers), `site/index.html` (the
   page describes the released build only, so change it in the release commit), `.github/release-notes.md`,
   and any preview in `media/previews/` that shows outdated things (frames are 640x400 = native pixels doubled,
   6 px black gaps).
2. Bump `VERSION` (e.g. `1.0.0b3`) and push to `main`. CI builds, smoke-tests and creates release
   `v<VERSION>` (a, b or rc makes it a pre-release) with `HAUNTED.EXE`, `HAUNTED.scr`, the zip and
   `SHA256SUMS.txt`; Pages redeploys. Pushing tags from an agent session is dropped by the proxy, so let
   CI make the tag.
3. Check: `gh run list`, the release through the REST API (`gh api repos/ASPDesignLabs/HAUNTED.EXE/releases/tags/v...`;
   GraphQL-based `gh` commands like `gh release view` are blocked in cloud sessions), download each asset,
   and fetch the live page.
4. The X card URL carries the version, so a new version refreshes link previews.
